# Выпуск релиза Clod Clash

Как собрать и опубликовать версию, которую установленные клиенты подхватят
через встроенный апдейтер.

## Как это работает

`tauri.conf.json` указывает апдейтеру два эндпоинта (пробуются по порядку):

```
https://github.com/Mrvibecodic/clod-clash/releases/download/updater/latest.json
https://github.com/Mrvibecodic/clod-clash/releases/latest/download/latest.json
```

Первый — «плавающий» релиз с тегом `updater`, куда после публикации версии
копируется её `latest.json`. Он нужен потому, что GitHub не считает
pre-release'ы «latest»: пока версии выходят как pre-release, второй эндпоинт
пуст, и обновления едут только через тег `updater`. Когда выйдет первый
стабильный релиз, заработает и второй эндпоинт как резервный.

Workflow `.github/workflows/release-clod.yml` по тегу `clod-v{версия}` собирает
инсталлеры (Windows x64, macOS arm64 и x64, Linux x64 deb+rpm), подписывает
артефакты апдейтера и прикладывает `latest.json` к черновику релиза. После
публикации релиз становится `latest`, и приложение видит обновление: молчаливый
апдейтер (`SilentUpdater`) проверяет при старте и раз в сутки, скачивает в кэш
и предлагает установить при следующем запуске. Если GitHub недоступен напрямую,
проверка и скачивание повторяются через собственное ядро (mixed-port).

## Ключи подписи

Пара ключей апдейтера уже выпущена: публичный лежит в
`src-tauri/tauri.conf.json` → `plugins.updater.pubkey`, приватный — в секретах
репозитория (`TAURI_PRIVATE_KEY`, `TAURI_KEY_PASSWORD`). Приватный ключ не
коммитится. Менять пару нельзя: клиенты со старым публичным ключом перестанут
принимать обновления. Если пару всё же пришлось перевыпустить
(`pnpm tauri signer generate -w ~/.tauri/clodclash.key`), обновить придётся и
конфиг, и оба секрета, а установленным клиентам понадобится ручная переустановка.

## Служба TUN и её версия

Клиентская библиотека службы (`clash_verge_service_ipc` в `src-tauri/Cargo.toml`)
и бинари самой службы (`SERVICE_VERSION` в `scripts/prebuild.mjs`) запинены на
**один и тот же тег** — и обновляются только парой. Клиент сверяет версию
установленной службы строго, поэтому расхождение пары означает вечное «фоновая
служба устарела» у каждого пользователя, которое не лечится переустановкой:
она ставит ту же несовместимую версию.

Поднимая версию службы: поменять тег в обоих местах, прогнать CI, выпустить
релиз. На Windows установщик обновления сам остановит старую службу, подменит
бинарь и запустит новый — без запросов прав, отдельный ремонт у пользователей
не понадобится. На Linux и macOS запущенный экземпляр службы обновлением не
перезапускается: до перезагрузки или ремонта из настроек будет работать старая
версия, и приложение предложит починить (один запрос пароля).

## Каждый релиз

1. Поднять версию в `package.json`, `src-tauri/tauri.conf.json`,
   `src-tauri/Cargo.toml` и `Cargo.lock` (секция `clash-verge`).
2. Дописать секцию `## v{версия}` в `UPDATELOG.md` — **двуязычную**: часть
   `<!-- lang:en -->` на английском и часть `<!-- lang:ru -->` на русском
   (см. существующие секции). Секция целиком попадает в `latest.json` и в
   тело GitHub-релиза; окно обновления в приложении показывает часть по
   языку интерфейса (русский → ru, любой другой → en). Пустая секция =
   фолбэк-текст, но клиенты 0.0.2 с пустыми notes вообще не могли нажать
   Update — секцию не пропускать.
3. Закоммитить, затем создать **аннотированный** тег (краткое русское
   сообщение — фолбэк для тела релиза, если секции в UPDATELOG нет) — и
   запушить:

   ```bash
   git tag -a clod-v0.0.4-alpha -m "Заголовок

   - что поменялось"
   git push origin main clod-v0.0.4-alpha
   ```

4. Всё остальное CI делает сам: workflow «Release Clod Clash» собирает
   черновик с инсталлерами, `*.sig` и `latest.json`, а финальный джоб
   `publish_release` после успеха всех платформ проверяет комплектность
   ассетов, публикует релиз как **pre-release** (тело — двуязычная секция
   из `UPDATELOG.md`, фолбэк — сообщение тега), вклеивает ту же секцию в
   `notes` файла `latest.json`, переписывает ссылки ассетов на публичные
   `browser_download_url` (tauri-action генерирует api.github.com-ссылки,
   пока релиз черновик) и переливает `latest.json` в плавающий релиз
   `updater`. С этого момента установленные клиенты видят новую версию —
   при старте или в течение суток. Неподписанный или подписанный чужим
   ключом артефакт апдейтер отвергает.
5. Если нужно перелить `latest.json` без пересборки (например, поправили
   UPDATELOG.md задним числом) — запушить тег
   `publish-clod-v{версия}` (workflow `publish-clod.yml`).

## Если что-то пошло не так

- Сборка упала на одной платформе — релиз останется черновиком, ассеты
  неполные, `latest.json` в `updater` не переливается: клиенты обновление не
  увидят. Исправить, удалить тег и пересоздать его.
- Ассеты собрались, а тело релиза или `latest.json` не то — правим
  `UPDATELOG.md` и пушим тег `publish-clod-v{версия}` (см. шаг 5), пересборка
  не нужна.
