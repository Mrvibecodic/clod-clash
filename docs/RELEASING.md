# Выпуск релиза Clod Clash

Как выпустить версию, которую установленные клиенты подхватят через встроенный апдейтер.
Сборка из исходников — в [BUILDING.md](./BUILDING.md).

## Коротко

1. Поднять версию в четырёх местах и дописать `UPDATELOG.md`.
2. Закоммитить, поставить тег `clod-v<версия>`, запушить ветку и тег.
3. Дождаться workflow «Release Clod Clash» (около 25 минут). Больше ничего пушить не нужно.

Версия с дефисом (`0.1.11-alpha.3`) — предварительная сборка, без дефиса — стабильная.

## Каналы обновления

Клиент берёт `latest.json` из служебных релизов на GitHub:

| Релиз | Что в нём | Кто читает |
| --- | --- | --- |
| `updater-prerelease` | манифест **любой** последней сборки, включая предварительные | клиенты с включёнными «Предварительными сборками» — первым |
| `updater` | манифест только **стабильной** сборки | все клиенты |
| `releases/latest` | манифест последнего обычного релиза GitHub | запасной адрес для всех |

* Адреса `updater` и `releases/latest` — в `src-tauri/tauri.conf.json`
  (`plugins.updater.endpoints`), адрес `updater-prerelease` зашит в
  `src-tauri/src/core/updater.rs`.
* Клиент с выключенными «Предварительными сборками» пропускает версию с дефисом, даже если увидит
  её.
* Манифест, в котором уже лежит версия новее, не перезаписывается.
* Если GitHub напрямую недоступен, проверка и скачивание повторяются через собственное ядро.

Фоновый апдейтер проверяет обновления при запуске и раз в сутки, скачивает в фоне и предлагает
«Установить сейчас» или «Позже». Портативная сборка сама не обновляется — новую версию берите со
страницы загрузки. Пока окно открыто,
новая версия показывается и окном обновления — по разу за запуск.

## Каждый релиз

1. **Версия** — в `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml` и
   корневом `Cargo.lock` (запись пакета `clash-verge`). Workflow проверяет, что тег совпадает с
   версией во всех четырёх местах.
2. **`UPDATELOG.md`** — секция `## v<версия>` только по-русски, без маркеров `<!-- lang:… -->`;
   каждый пункт — одной строкой, только то, что заметит пользователь. Она становится телом
   релиза и `notes` в `latest.json`; окно обновления показывает её как есть. Секцию не
   пропускать.
3. **Коммит и тег:**

   ```bash
   git commit -am "chore(release): 0.1.12-alpha.1"
   git tag -a clod-v0.1.12-alpha.1 -m "0.1.12-alpha.1"
   git push origin main clod-v0.1.12-alpha.1
   ```

   Тег — на последнем коммите пуша: проверки на `main` идут только для вершины пуша, и у
   коммита под ней их нет — такой релиз не опубликуется.

4. **Дальше CI сам** (`.github/workflows/release-clod.yml`):
   * собирает Windows x64 (установщик и портативный zip), macOS arm64 и x64, Linux x64 (deb и
     rpm) и подписывает артефакты апдейтера;
   * публикует, только когда проверки того же коммита на `main` (Clippy Lint с тестами Rust и
     Frontend Check) прошли; тег на коммите, которого нет на `main` или который не был вершиной
     пуша, не публикуется;
   * проверяет, что все ассеты на месте, и публикует релиз: галка pre-release ставится сама,
     если в версии есть дефис; тело — секция из `UPDATELOG.md` (если её нет — сообщение тега);
   * убирает версию из имён ассетов — так работают постоянные ссылки
     `/releases/latest/download/<файл>`;
   * раскладывает `latest.json`: в `updater-prerelease` всегда, в `updater` — только для версии
     без дефиса.

## Ключи подписи

Публичный ключ апдейтера — в `src-tauri/tauri.conf.json` → `plugins.updater.pubkey`, приватный —
в секретах репозитория (`TAURI_PRIVATE_KEY`, `TAURI_KEY_PASSWORD`). Приватный ключ не
коммитится. **Пару менять нельзя:** клиенты со старым публичным ключом перестанут принимать
обновления, и им понадобится ручная переустановка. Сборку, подписанную чужим ключом или без
подписи, апдейтер отвергает.

## Версия службы TUN

Клиентская библиотека службы (`clash_verge_service_ipc` в `src-tauri/Cargo.toml`) и бинарники
службы (`SERVICE_VERSION` в `scripts/prebuild.mjs`) закреплены на **одном и том же теге** и
обновляются только вместе. Клиент сверяет версию службы строго: расхождение — это вечное
«фоновая служба устарела» у всех пользователей, которое переустановка не лечит.

На Windows установщик обновления сам останавливает старую службу, подменяет её и запускает
новую — без запроса прав. На Linux и macOS запущенная служба обновлением не перезапускается:
до перезагрузки или починки из настроек работает старая версия, и приложение предложит починить
(один запрос пароля).

## Если что-то пошло не так

* **Сборка упала на одной платформе** — релиз остаётся черновиком, манифесты не трогаются,
  клиенты обновление не видят. Исправить, удалить тег и черновик, поставить тег заново.
* **Проверки коммита красные** — релиз остаётся черновиком, манифесты не трогаются. Исправить и
  выпустить новую версию. Если проверка упала случайно (сбой раннера), перезапустить её, а затем в
  прогоне «Release Clod Clash» — упавшие задачи (Re-run failed jobs).
* **Публикация не прошла, а все ассеты собрались и проверки коммита зелёные** — запасной путь: тег
  `publish-clod-v<версия>` запускает `publish-clod.yml`. Он так же ждёт зелёных проверок коммита
  релиза, публикует релиз (pre-release — по
  дефису в версии), убирает версию из имён ассетов, раскладывает `latest.json` тем же скриптом
  и удаляет отработавший тег. Тело
  релиза он берёт из **сообщения этого тега**, а не из `UPDATELOG.md`. Если `release-clod.yml`
  отработал нормально, этот тег не нужен.
